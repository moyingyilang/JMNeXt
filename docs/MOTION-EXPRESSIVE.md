# 动效设计：从「一堆曲线」到一套可判定的语言

> 这是 1.8.x 之前就提过、一直没真正做成的那件事。本文是**设计契约**，不是灵感清单：
> 每一条都要能回答「解决什么感知问题」，并且**可判定**（写成单测或帧率指标，而不是"看着还行"）。

## 零、先厘清一个失败尝试（如实记录）

我尝试直接读本机 material3 库里的 `MotionScheme`（`expressive()` / `standard()` 的 spring 参数）作为基准，
结果是 **`MotionScheme` 在当前版本是 `internal`**，测试代码编译不过：

```
e: Cannot access 'interface MotionScheme': it is internal in file.
e: Cannot access 'fun expressive(): MotionScheme': it is internal in 'MotionScheme.Companion'.
```

结论有两条，都很重要：

1. **不要**把动效 token 建立在库的未公开实现上 —— 版本一动就散；
2. 所以 token 由**我们自己定义**（现有 `JmEasing` 已经是这个路子），
   权威性靠**帧率与观感实测**建立，而不是靠"抄官方数值"。

## 一、三条判断标准（一切动效先过这三关）

| 标准 | 含义 | 不满足时的处理 |
| --- | --- | --- |
| **可中断** | 动画进行中用户再次输入，状态必须能从中途接上（而不是排队或跳变） | 用 `Animatable`/`animateTo` 而不是重启动画 |
| **有因果** | 元素从"它来的方向"进入、回到"它去的地方"退出（空间连续性） | 检查位移起点/终点是否与触发控件的位置关系一致 |
| **不抢戏** | 每屏同一时刻**只有一处**主运动；其余用淡入/微位移 | 删掉次要运动 |

## 二、token 表（本项目口径）

时间单位 ms；曲线用 cubic-bezier 表述，便于两端（Compose / Qt）复用同一组数字。

| 交互 | 时长 | 曲线 | 位移/缩放 | 解决什么 |
| --- | --- | --- | --- | --- |
| 按压反馈 | 90 | `standard` (0.33,0,0.67,1) | 缩放 0.97 → 1.0 | 指尖"按下去了"的即时确认（<100ms 才像触觉） |
| 列表项进入 | 220 | `fluent` (0.16,1,0.3,1) | Y +12dp → 0，透明度 0 → 1 | 内容"长出来"而不是"跳出来" |
| 列表项移除 | 160 | `inCubic` (0.55,0.055,0.675,0.19) | 高度 → 0 + 透明度 → 0 | 退出要**比进入快**，否则显拖沓 |
| 前进转场 | 300 | `decel` (0.1,0.9,0.2,1) | 新页 X 100% → 0，旧页 0 → −25% | 深度隐喻：新页从右推入 |
| 返回转场 | 260 | `outCubic` (0.215,0.61,0.355,1) | 反向，且**比前进快** | 返回是"撤销"，用户已知道要去哪 |
| 共享元素（hero） | 320 | `emphasized` 近似 (0.2,0,0,1) | 位置+尺寸连续插值 | 让人相信"这就是同一张图" |
| 底部栏展开/收起 | 240 / 200 | `decel` / `inCubic` | 高度 + 内容淡入（**错开 40ms**） | 先给容器、再给内容，避免内容被裁切 |
| 对话框 | 进入 200 / 退出 150 | `decel` / `inCubic` | 缩放 0.92 → 1 + 遮罩 0 → 0.4 | 对话框是"聚焦"，不是"飞入" |
| 阅读器工具栏 | 显 180 / 隐 150 | `standard` | 顶/底栏 Y ±100% | 沉浸阅读时工具栏必须**迅速让位** |
| 加载态 | 骨架 1200 循环 | 线性（唯一允许线性处） | 扫光位移 | 线性=进度未知，反而是正确语义 |
| 错误态 | 200 + 抖动 3 次 | `outCubic` | X ±4dp 衰减 | 抖动只在"有输入被拒"时用，且必须衰减 |

**硬约束（可写成单测）**：

1. 所有时长必须在 `[90, 600]` 区间；退出类时长必须 ≤ 对应进入类时长；
2. 除加载态外，**不允许线性曲线**；
3. 同一屏的入场动画必须共享同一曲线族（不允许一屏三套缓动）。

| 差距 | 表现 |
| --- | --- |

| 缺退出语义 | 多数动画只有进入，退出用同一个 spec（导致"退出和进入一样慢"） |

## 四、落地步骤（每步可独立验收）

1. **token 落地**：`ui/theme/Motion.kt` 定义 `JmMotion`（上表的类型安全映射），加单测覆盖上面三条硬约束；
2. **替换硬编码**：全局搜 `tween(` / `spring(`，逐处改为按交互取 token；
3. **退出语义**：给 `AnimatedVisibility` 的 `exit` 分支统一用"更快"的 token；
4. **共享元素**：`SharedTransitionLayout` 接详情页 hero（图片 + 标题）；
5. **reduce-motion**：读系统动画缩放（`Settings.Global.ANIMATOR_DURATION_SCALE`）→ 为 0 时退化为纯淡入（时长 120ms）；
6. **帧率验证**：`dumpsys gfxinfo <pkg>` 或 `FrameMetrics` 记录关键路径的 90/95 分位；目标：列表滚动与页面转场 **95 分位 ≤ 16.7ms**；
7. **桌面端对齐**：`desktop/Motion.kt` 用同一组时长/曲线数字（Qt 组件那边同样按此表）。

## 五、验证方式（明确区分）

- **可自动验证**：token 映射正确性、三条硬约束、reduce-motion 降级分支；
- **需真机/目视**：观感是否"更美观"（这是主观项，最终由用户确认）；
- **需测量**：帧率分位数（我可以在设备上用 `dumpsys gfxinfo` 取，但要先装上带改动的包）。

## 六、不做什么

- 不做"每个控件都加动画"：没有因果关系的运动只会让界面显得廉价；
- 不做弹跳（bounce/overshoot）除非表达"越界后回弹"这一物理含义；
- 不为了动效牺牲启动时间或首帧。

## 七、帧率基线（2026-10-25，真机实测）

设备：本机（aarch64 Android 15/16，具体型号未记）。构建：`app-full-debug.apk`（2.1.9 之后、动效 token 接入版）。
采集方式：`pm install -r` 覆盖安装 → `am force-stop` + `am start` 冷启动 → 等 8s → `dumpsys gfxinfo com.jmnext reset`
→ 5 次滑动 + 1 次点击 → `dumpsys gfxinfo`。

| 指标 | 数值 |
| --- | --- |
| Number Missed Vsync | **0** |
| Number Slow UI thread | **0** |
| Number Slow issue draw commands | **0** |
| 帧耗时分布 | 集中在 7–9ms（7ms 206 帧、8ms 272 帧、9ms 308 帧），共约 1122 帧 |
| 50th gpu percentile | 6ms |
| 90th gpu percentile | **7ms** |
| 95th gpu percentile | **10ms** |

**判定**：95 分位 10ms < 16.7ms（60fps 预算），当前动效在**滚动与点击路径上没有掉帧**。
这条基线的作用是：以后任何动效改动都要再测一次并与之对比，**不允许靠"看起来还行"结案**。

**未覆盖的路径**（下一轮补测）：页面前进/返回转场、hero 共享元素、阅读器工具栏显隐、底部栏展开 —— 这些需要逐项
`gfxinfo reset` + 单次操作分别采集，滚动路径的基线不能代表它们。

## 八、逐路径帧率测量（首轮，2026-10-25）

方法：`dumpsys gfxinfo com.jmnext reset` → **只做一次**动作 → 采集，避免把别的动作混进统计。

| 路径 | 50th | 90th | 95th | 99th | 判定 |
| --- | --- | --- | --- | --- | --- |
| 滚动（上/下 5 次） | 6ms | 7ms | **10ms** | — | 达标（基线） |
| Tab 切换 | 10ms | 15ms | **16ms** | 18ms | **贴线**（16.7ms 预算） |
| **返回主界面** | 11ms | 18ms | **22ms** | **113ms** | **超标：有一次明显卡顿** |

三条结论：

1. **静态/滚动路径是健康的**（95 分位 10ms）；
2. **转场路径不行** —— 返回时的 99 分位 **113ms** 意味着用户实际会看到一次顿挫，而 95 分位 22ms 说明这不是孤例；
3. Tab 切换 16ms 属"贴线"，任何新图层/新模糊叠上去就会破线。

**下一步的针对性方向**（不猜，按数据）：

- 返回路径要查：退出转场是否同时触发**整页重绘**（列表重新组合/图片重新测量），以及 `SharedTransitionLayout` 的 `BoundsTransform` 是否在返回时走了完整测量流程；
- 若确认是整页重组，改用"先出转场、后重组"或对列表项做 `key` 稳定化；
- Tab 切换可考虑缩短位移距离（而非缩短时长），减少每帧绘制面积。

> 说明：本轮的日志提取脚本把"命令回显"也写进了日志，导致按关键字提取时混入噪声；下一轮会先修日志格式（回显压成单行）再做批量提取，避免读出错误结论。

## 九、逐路径测量（第二轮，修正版）

**上一节（第八节）的数据作废**，原因是两个方法错误：

1. **标注错了动作**：所谓"返回主界面"实际执行的是 `input tap 270 2200`（点底部栏 Tab），不是返回；
2. **毫秒解析错**：`grep -oE '[0-9]+'` 抓到的是 `50th` 里的 `50`，不是 `12ms` 里的 `12`。

这一轮改用不依赖坐标猜测的动作（`swipe` / `keyevent`），并把解析改成 `sed -n 's/.*percentile: \([0-9]*\)ms.*/\1/p'`：

| 路径 | 50th | 90th | 95th | missedVsync | slowUI | slowDraw |
| --- | --- | --- | --- | --- | --- | --- |
| 冷启动 | — | — | — | — | — | — |
| 滚动下（swipe） | 6ms | 8ms | **10ms** | 0 | 0 | 0 |
| 滚动上（swipe） | 6ms | 10ms | **10ms** | 0 | 0 | 0 |
| 底部栏中间按钮（tap） | 8ms | 10ms | **12ms** | 0 | **1** | **1** |
| 返回键（KEYCODE_BACK） | 数据无效 | — | — | — | — | — |

**冷启动**：`am start -W` → `TotalTime: 190ms`（第二次测为 147ms，波动来自系统状态）。

**结论（这次可信的）**：滚动路径 95 分位 10ms、底栏点击 12ms，均在 60fps 预算内；
`slowUI=1`、`slowDraw=1` 各出现一次，属偶发并非稳定超时。
**返回路径这次没测到**（按下返回键时页面已退出，`gfxinfo` 读到的是旧值），需要用"从详情页返回列表"这类**不退出应用**的动作重测。

## 十、下一步（避免再犯同样的方法错误）

1. 测"详情 → 返回"时，必须保证**从二级页面返回**（不退出 App），并且测量前确认前台仍是本应用；
2. 每次测量记录**动作语义**（点哪里、第几屏），而不是事后回忆；
3. 解析统一走 `percentile: Nms` 的 `sed` 规则，不再用 `grep -oE '[0-9]+'`。

## 十一、导航转场测量（第三轮）

用 `uiautomator dump` 取**真实控件坐标**（不再用猜测的点），流程：冷启动 → dump → 取可点击节点中心 → 点击 → reset+采集。

| 路径 | 50th | 90th | 95th | missedVsync | slowUI | slowDraw |
| --- | --- | --- | --- | --- | --- | --- |
| 进详情（前进转场） | 6ms | 7ms | **7ms** | 0 | 1 | 1 |
| 返回（back 转场） | 数据无效 | — | — | — | — | — |

**前进转场是健康的**（95 分位 7ms）。**返回仍然没测到**：点击后并没有真正进入详情页，
随后 `keyevent 4` 直接把应用退出了，`gfxinfo` 读到的是旧值（表现为 4950 这种离谱数字）。

**方法上的教训（第三次同类问题）**：不能只验证"发送了动作"，必须**验证动作生效**。
下一次的硬性要求：每次点击后先 `uiautomator dump` 确认页面已切换（例如出现"章节/简介"这类详情页元素），
确认后再 reset 并采集；若没切换，换节点重试，而不是直接读数。

## 十二、转场测量的阻塞（如实记录，暂停这一路）

连续四轮尝试都**没能测到"详情→返回"**，每次失败原因都不同（这正是记录的价值）：

| 轮次 | 做法 | 失败原因 |
| --- | --- | --- |
| 1 | 点 `(270,2200)` | 那是底部栏 Tab，动作标错，且读数解析错（抓到 `50th` 的 50） |
| 2 | `keyevent 4` 直接按返回 | 页面已退出，`gfxinfo` 读到旧值（4950） |
| 3 | `uiautomator` 取第一个 clickable | 取到空 View，未导航 |
| 4 | 取卡片中心 `(307,890)` 点击 | **点击不生效**：dump 复查仍在列表页（"更多/首页"与作品标题都在） |

第 4 轮说明"点击不导航"是当前的**事实性阻塞**，而不是我又选错了节点：卡片确实在 `[60,560][555,1220]`，
但我发了 `input tap 307 890` 之后页面没有变化。可能原因（尚未验证）：页面被某个浮层遮挡、该卡片需要
长按/滑动手势、或 App 在启动后弹了某个提示层。

**决定**：暂停"用 input 事件测转场"这条路，改走下面两条之一（二选一，取决于你）：

1. **Instrumentation 里测**：写 `androidTest` 用 `composeTestRule.mainClock` 直接推进转场并记录帧，
   不依赖真实触摸 —— 可靠，但要接 androidTest 基础设施；
2. **人工录屏 + 帧提取**：你手动操作一遍，录屏后我按帧分析（最贴近真实观感，也最省搭建成本）。

在此之前，**能继续推进的是不需要设备交互的部分**：把 `press` / `listEnter` / `listExit` / `dialogIn/Out`
接到组件上（编译 + 单测可验证），以及桌面端 `Motion.kt` 对齐。

## 十五、转场帧率（已采到，带校验）

按第十四节的配方固化成脚本后一次跑通（`uiautomator` 取 **y>1200 的标题节点** → 先 reset 再 tap →
**校验 dump 出现「作者」** 才算数；返回同理校验「首页/更多」）：

| 路径 | 50th | 90th | 95th | missedVsync | 校验 |
| --- | --- | --- | --- | --- | --- |
| 前进（列表→详情） | 8ms | 9ms | **14ms** | 0 | dump 含「作者：」通过 |
| 返回（详情→列表） | 9ms | 14ms | **16ms** | 0 | dump 含「首页/更多」通过 |
| 滚动（上/下） | 6ms | 8–10ms | **10ms** | 0 | — |
| 底栏点击 | 8ms | 10ms | **12ms** | 0 | — |

**判定**：四条路径都在 60fps 预算（16.7ms）内；**返回路径 95 分位 16ms 最贴线** —— 它与"退出比进入快"
的设计（260ms vs 300ms）一致，但余量只有 0.7ms，再叠加任何新图层就会破线。这一点应作为后续改动
的**回归警戒线**。

**方法上的结论**（比数字更重要）：这次成功不是因为"试对了坐标"，而是因为把三件事固化了——
① 等布局稳定再 dump；② 按位置过滤节点（y>1200）而不是按出现顺序；③ **用页面内容校验动作是否生效**，
校验不过直接作废。前六次失败全都可以归因到这三条没做到。
