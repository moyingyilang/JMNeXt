# Kotlin 编译加速：自研工具链的可行性与路径

> 起点：用户提出「用 IR 解决各种寻路变量与脱糖问题，最后并行编译，达到 ninja 的速度」。
> 这份文档只回答两件事：**这条路能不能走**、**先做哪一步才不浪费时间**。

## 一、先把"慢在哪"说清楚（否则一切方案都是猜）

Kotlin 编译慢通常不是单点，而是四段叠加：

| 阶段 | 内容 | 本项目的影响 |
| --- | --- | --- |
| 1. 前端（FIR/K2） | 解析、**全模块**符号解析、重载决议、扩展函数/内联检查 | 与模块大小成正比；**语义上必须能看到整个模块** |
| 2. 后端（IR lowering） | 脱糖：默认参数、内联、lambda/indy、协程状态机、JVM default | CPU 密集，但**大部分是文件/函数局部**的 |
| 3. 编译器插件 | Compose 稳定性推断、kotlinx.serialization | Compose 的稳定性推断是本项目最贵的一块之一 |
| 4. 构建/打包 | Gradle 配置、AGP 资源、**R8**、签名 | 本项目的 **release 构建里 R8 常常比编译本身更久** |

**关键结论**：你说的"寻路变量"属于第 1 段，而第 1 段**在 Kotlin 语义下无法避开全局解析**
（扩展函数、重载、`expect/actual`、内联跨模块都要全局视图）。所以：

> **不可能"用 IR 省掉解析"** —— IR 是解析的**产物**，不是替代品。
> 真正能并行的，是**第 1 段之后**：lowering 与写 class 文件。

## 二、"达到 ninja 速度"的真实含义

ninja 快是因为：**每次只编受影响的文件、且这些文件彼此独立**。
Kotlin 目前的粒度是 **模块**（本项目 2 个 Kotlin 模块），所以：

- 模块级并行 → 只有 2~3 个任务，**并行度用不起来**（这也是 Gradle 并行在本项目收益有限的原因）；
- 想快，必须把粒度降到 **文件级**，而这要求：**前端只跑一次（全局解析），后端按文件并行**。

这正是可以自研的部分，也是最难的部分。

## 三、可行的自研形态（建议的一句话版本）

> **共享一次前端（FIR 会话 + 符号表 + 每文件 IR），按文件并行做 lowering 与 class 写出，最后并行打包。**

具体拆解（用 `kotlin-compiler-embeddable` 当库）：

1. **单次前端**：用 K2 API 建 `FirSession` 拿到全模块符号表与每文件 `IrFile`；
2. **并行 lowering**：对每个 `IrFile` 独立跑 lowering（Compose/serialization 这两个插件是 **IR 扩展**，可以在全局解析之后按文件施加）；
3. **并行写盘**：每文件写自己的 `.class`（IR 到字节码是文件内封闭的）；
4. **增量**：以「文件 + 依赖签名」为 key 缓存阶段 1 的结果，改一个文件只重跑它的 lowering。

**风险要说在前面**：
- K2 的内部 API **不稳定**，随 Kotlin 版本变动（本项目已跟到 2.4.x）；
- Compose 插件的 lowering 是否真的 file-local 需要实测（有跨文件稳定性推断，可能要回退到"每个编译单元一组文件"）；
- 需要与 kotlinc 做**产物等价性校验**（ABI/字节码差异），否则"编得快但编错了"毫无意义。

## 四、分阶段路线（每阶段都有可验收指标）

| 阶段 | 做什么 | 验收指标 | 预估 |
| --- | --- | --- | --- |
| **0. 量化** | 用 Gradle build scan / `--profile` 拆出：配置、前端、后端、插件、R8、资源各占多少 | 一张带数字的表，指出**最大项** | 半天 |
| **1. 榨干现有能力** | configuration cache、build cache、常驻 Kotlin daemon、`-Xjvm-default=all`、**开发迭代不跑 R8**（debug 变体）、`composeCompiler` 稳定性配置 | 增量编译时间下降 ≥30%（先测再改） | 1–2 天 |
| **2. 原型：并行后端** | 用 compiler-embeddable 做「一次前端 + 按文件并行 lowering + 并行写 class」，**只针对 `:shared` 模块**（纯 JVM、无插件、最好验证） | 与 kotlinc 产物 **ABI 等价**；`:shared` 编译时间下降（目标 2x） | 1–2 周 |
| **3. 扩到 `:app`** | 加 Compose/serialization 插件支持；处理跨文件稳定性推断的边界 | `:app` 增量编译下降；产物通过现有 `assemble` 与真机冒烟 | 数周 |
| **4. 产品化** | 包成 Gradle 任务/守护进程；失败可回退到 kotlinc | 可开关、可回退、CI 与本地同用 | 数周 |

**阶段 1 必须先做**：它便宜、无风险，而且能告诉你"最大项到底是不是 Kotlin 编译"。
如果阶段 0 显示 R8 或资源处理才是最大项，那阶段 2 的自研后端就不值得做。

## 五、可复用的现成方案（在自研之前值得先试）

| 方案 | 适用 | 对本项目的判断 |
| --- | --- | --- |
| Gradle configuration cache + build cache | 全场景 | **立刻可用**，最便宜 |
| Buck2（Meta） | 大仓、多语言 | Kotlin 规则可用，但 Android 支持弱；本项目规模不值 |
| Bazel + `rules_kotlin` + persistent workers | 大仓 | 见 `docs/bazel-feasibility.md`：Android 侧代价高 |
| Kotlin 官方 K2 增量（classpath snapshot） | 全场景 | 先打开并测量 |

## 六、我的建议

1. **先做阶段 0 + 1**（半天到两天），拿到"时间花在哪"的真实数字；
2. 若 Kotlin 编译确为最大项，**只在 `:shared` 上做阶段 2 原型**——它没有插件、纯 JVM，是唯一能用小成本验证"并行后端"想法的地方；
3. 原型若不达 2x，就停在这里，把精力放回产品功能；若达 2x，再谈扩到 `:app` 与产品化。

**不建议**的路线：自研前端（替代 FIR）——那等于重写 Kotlin 的名字解析与重载决议，成本以年计，且会立刻失去与 Compose/序列化插件的兼容性。
